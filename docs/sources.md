# CTI sources

Notes on each integration: how it is queried, what it needs and anything that affects how its result is read. The coverage table (which indicator types each source supports) and the API key list are in the [README](../README.md#-sources). Scoring rules per source are in [admin.md § 6](admin.md#6-reference-defaults-and-scoring-rules-per-source).

## Sources without an API key

**Tor Exit Nodes, MITRE ATT&CK, RIPEstat, PhishTank, TweetFeed, CIRCL hashlookup, RDAP, Tranco, Malpedia, Spamhaus, OpenPhish, SSLBL, NVD, CISA KEV and EPSS** are free public datasets/APIs: always on, toggleable like any other source.

- **MITRE ATT&CK** — the backend downloads the ~50 MB STIX dataset from GitHub and caches it in memory for 24 h (the first lookup after a cold start takes a few seconds). Besides actor lookups, it feeds the Summary's actor detection and malware alias merging (`GET /mitre/aliases`). Without internet those fall back to the built-in family table.
- **RIPEstat** — routing (ASN / prefix) and abuse-contact data from the RIPE NCC registry.
- **PhishTank** — the `checkurl` API works anonymously; an optional `PHISHTANK_API_KEY` only gives higher request priority.
- **TweetFeed** — a free (CC0) feed of IOCs shared by the infosec community on X/Twitter, queried by exact match over the last 365 days. Reports are unvetted (a legitimate service hosting abused content can show up), so its risk subscore is capped at 7 and it never issues a clean verdict. For reported IPs/domains it also feeds GeoIP / ASN / ISP into the Summary.

- **CIRCL hashlookup** — known-good file hashes (MD5 / SHA-1 / SHA-256 / SHA-512) from NIST's NSRL, Linux distribution packages, app stores… A hit is an explicit **clean** verdict for a hash, the only hash source that gives one — except when the record carries `KnownMalicious` (the file is also in a malware repository: EICAR, dual-use tools such as Metasploit), which turns it into context only. Not found is no data: most files are simply not catalogued.
- **RDAP** — registration data of the domain (of the URL's host for URLs), straight from the TLD registry found through IANA's bootstrap file (cached 24 h). Subdomains are reduced to the registered domain with the Public Suffix List bundled in `tldextract` (no network fetch). Its point is **domain age**, computed at lookup time and frozen in the history: < 7 days → 7, < 30 days → 5; an older domain issues no verdict (compromised sites are old too). Some ccTLDs (.es, .de…) publish no RDAP service: the card says so (`NoRdapService`).
- **Tranco** — research-grade ranking of the top 1M domains (aggregated over 30 days, hard to manipulate). A registered domain in the top 100 000 is an explicit **clean** verdict; outside it, context only. A **subdomain never inherits** its parent's rank (`evil.duckdns.org` → `duckdns.org` is #134): it shows as context with a warning. Popular ≠ safe content, so the risk weight is low (2). The API allows about one request per second; the backend spaces requests.
- **Malpedia** (Fraunhofer FKIE) — threat actor profiles with synonyms, suspected sponsor, targeted sectors, references and the **malware families attributed to the actor**, which feed the Summary's families and actor relations. Name search matches synonyms ("Fancy Bear" → APT28). Works without a key; an optional `MALPEDIA_API_KEY` raises the rate limit.

- **Spamhaus** — DNS queries to **ZEN** for IPs (SBL, CSS, XBL, DROP, PBL) and to the **DBL** for domains and URL hosts (the registered domain and, if different, the full host), plus the **ASN-DROP** list for ASNs (downloaded, cached 12 h) — the only source that gives ASNs a risk verdict. Scored by return code: DROP / ASN-DROP and DBL phishing / malware / C&C → 9, SBL → 8, XBL and DBL spam → 7, CSS → 6, abused legitimate domains → 5–6; the PBL (dynamic / end-user ranges) is context only. **Spamhaus refuses queries arriving through public resolvers** (8.8.8.8, 1.1.1.1…): the backend uses the container's resolver, i.e. the host's; set `SPAMHAUS_DNS_SERVER` in `backend/.env` to choose one, or add a free **DQS key** (`SPAMHAUS_DQS_KEY`, Connectors), which works from any resolver. A refused query shows as `ResolverBlocked`. Free for low-volume, non-commercial use — check [the terms](https://www.spamhaus.org/organization/dnsblusage/).
- **OpenPhish** — the community feed (a few hundred currently active phishing URLs), downloaded and kept for an hour. URL: listed itself → 9, another listed URL on the same host → 6. Domain / IP: phishing URLs whose host *is* that domain (or `www.`) or IP → 7; subdomains' URLs never count for the parent. Not listed is no data — the feed is small.
- **SSLBL (abuse.ch)** — the SSL certificate blacklist (SHA-1 fingerprints of certificates used by botnet C&C / malware servers), downloaded and kept for an hour. It only answers for 40-character hashes; any other hash is reported as not applicable. Its IP and JA3 blacklists are no longer maintained (deprecated in 2025 / 2021) and are not used. The listing reason ("Vidar C&C") feeds the Summary's malware families.
- **Vulnerabilities (CVE)** — three sources for the `cve` type. The identifier is normalised (`cve-2021-44228`, `CVE_2021_44228` → `CVE-2021-44228`); anything else is rejected with `BadRequest` without querying.
  - **NVD (NIST)** — the CVE record: description, CVSS (newest version, NVD's own score first), CWE weaknesses, CISA's SSVC decision points (exploitation none / PoC / active, automatable), affected products (from the CPE configuration, trimmed to 25) and references (exploit and vendor-advisory ones first). Works without a key at ~5 requests per 30 s; a free `NVD_API_KEY` (Connectors) raises it to 50. The NVD answers a rate-limited client with HTTP 403, shown as `RateLimitExceeded`; recently published CVEs may still be *Awaiting Analysis* without a CVSS (no verdict until scored).
  - **CISA KEV** — the Known Exploited Vulnerabilities catalog (~1 800 CVEs with confirmed exploitation in the wild), downloaded and kept for 3 hours. Listed → 9, or 10 when CISA knows it's used in ransomware campaigns. Not listed is no data: KEV only holds exploitation CISA has confirmed.
  - **VulnCheck KEV** (`VULNCHECK_API_KEY`, free Community token; tokens unused for 30 days expire) — VulnCheck's catalog of known exploited vulnerabilities, a superset of CISA KEV: exploitation reported publicly (with the source URLs, earliest first), seen by VulnCheck's own canaries, and links to public exploit code in VulnCheck XDB. It usually lists a CVE days or weeks before CISA, and lists CVEs CISA never adds; the card says when a CVE is not (yet) in CISA KEV. Listed → 9, ransomware → 10; not listed is no data.
  - **EPSS (FIRST)** — the daily probability that the CVE is exploited in the next 30 days, with its percentile and the last 30 days of history (sparkline on the card). Under 1 % is an explicit low-risk (clean) verdict.
- **Companies** — six keyless sources for the `company` type. A name is ambiguous, so the home page first lists **Wikidata** candidates (`GET /company/resolve`); picking one searches `Name (domain, Q-id[, LEI])`, which pins the entity for every source and the history. The same format can be typed by hand (`Acme (acme.com)`); a bare domain also works. Name-based sources use the name; domain-based ones need a domain and answer `NeedsDomain` without one (left out of Knowledge, like a transient failure).
  - **Wikidata** — sector (industry, or the item's type when no industry is recorded), country, headquarters, parent / owners, subsidiaries with their countries, founding date, employees, tickers, website and LEI. "Countries" is where it has a presence (own country, HQ, subsidiaries), not where it sells. Without a Q-id the first organisation whose official website matches the domain is used, or the first organisation with that name (flagged *best match*, basic record). Context only.
  - **GLEIF** — the legal entity (LEI): legal name, jurisdiction, registered and HQ addresses, status, direct and ultimate parent, direct subsidiaries by country. The LEI comes from the indicator, from Wikidata, or from a legal-name search that must be exact once legal forms are ignored (*Apple Inc.* = *APPLE INC*) and unambiguous; otherwise the card lists candidates and has no record. Context only.
  - **ransomware.live** — victims claimed on ransomware groups' leak sites (dark web): group, dates, sector, country, description. The full victims list (~25 MB) is downloaded and kept 6 h (the last good copy of it and of `groups.json` is also saved, compressed, in `backend/data/feeds/`, so a restarted backend starts from it — no re-download within the 6 h, and a stale copy is served if the 30-minute limit blocks the refresh), because the free API allows one search per minute and the dump one download per 30 min per IP; while the list has never loaded, the search API is used. A victim counts when its domain is the company's or its name is the same ignoring case, accents and legal form; names that only *contain* it are listed as similar, never counted. Leak-site (.onion) addresses are shown as text, never linked. For **threat actors**, the group profiles (`groups.json`, ~2 MB, same 6 h cache) are matched on name or alternative name, ignoring words like *ransomware* / *group* and including versions ("LockBit" → lockbit, lockbit2, lockbit3…, "BlackCat" → alphv); the card shows the profile (description, RaaS, lineage, leak sites online) and the actor report lists each leak site / chat / file server (`locations`: address as text, type, page title, online at the last scrape, last check) and the group's victims from the same dump: total, last claim, claims in the last 30 / 90 / 365 days, top sectors and countries. APT groups without a leak site are not tracked. Context only; its last claim feeds the actor **Activity**.
  - **Hudson Rock** (Cavalier free OSINT API) — infostealer infections linked to the domain: infected employees (corporate credentials at risk), users / customers, third parties, last infection dates, stealer families and the exposed login URLs. Counts only: no credentials or personal data are retrieved or stored. Hudson Rock evaluates every domain, so zero infections is an explicit **clean** verdict. Needs a domain.
  - **Have I Been Pwned** — public breaches of the company's own services (`/breaches?domain=`, keyless): date, accounts, data classes, verified. Spam lists and fabricated breaches are shown but not counted. Breaches of *other* sites that include the company's employees need domain verification and are not queried. Needs a domain.
  - **GDELT DOC 2.0** — worldwide news of the last 90 days that mention the company together with incident words (cyberattack, ransomware, data breach, hackers, ciberataque…). Only headlines that name the company count for Knowledge; the rest are listed. Context only: a headline is not a confirmed incident. GDELT allows one request every 5 s per IP (spaced by the backend) and may throttle busy egress IPs for longer — then the card shows a rate-limit error.
- **Feodo Tracker** is deliberately not integrated: after the Emotet / QakBot takedowns its list holds a handful of entries, so it would almost never match while still diluting Knowledge for every IP.

## Passive lookups (nothing is submitted)

- **urlscan.io** queries the public index of scans already submitted by others — it never submits your indicator, so nothing you look up becomes visible to third parties.
- **ANY.RUN** uses the **TI Lookup** API: a search over existing sandbox intelligence (~180-day window), not a live detonation.
- **Hybrid Analysis** uses `/search/terms` and `/search/hash` over existing Falcon Sandbox reports, not a live submission.

## Shared credentials and limits

- **ThreatFox, URLhaus, MalwareBazaar and YARAify** share the unified abuse.ch key (`ABUSECH_AUTH_KEY`), but are independent, individually toggleable sources.
- **Recorded Future** (`RECORDED_FUTURE_API_KEY`) — four APIs with the same token:
  - *IP / domain / URL / hash* (Connect API): risk score and rules, first / last seen, the **AI summary** (`aiInsights`) and the **threat lists** the IOC is on. Then the **Links API**: actors, malware, ATT&CK techniques and infrastructure that Insikt Group or RF's technical analysis link to the IOC. Those actors and malware feed the Summary only when the IOC's RF risk is ≥ 25 ("Suspicious" and above): a benign IOC is linked to whatever uses it (8.8.8.8 to Mirai, google.com to Kimsuky). Two requests per lookup.
  - *Threat actor* (Threat API): `/threat/actor/search` matches any alias ("APT28" → BlueDelta); the card shows categories, aliases, the actor's links (malware, techniques, organisations) and its infrastructure, each IOC one click away from its own lookup. If the actor is on **your organisation's Threat Map**, the card shows the intent and opportunity RF estimates towards you; the map (every actor relevant to the organisation, ~700 KB) is cached 6 h. Context only, never a risk verdict. Two requests (three when the map is refreshed).
  - *Company* (Entity Match + Links API): `/entity-match/match` (type Company) on the company name; the aliases of the first five candidates (`/entity-match/entity/<id>`) pick the one whose name or alias matches ("Iberia" → the airline, whose aliases include *Iberia Líneas Aéreas de España*), otherwise RF's best match, flagged as closest. Then the company's links: threat actors and ransomware groups, malware, ATT&CK techniques and infrastructure (phishing URLs, domains, IPs) RF ties to it; the actors and malware feed the Summary relations. The card also lists the other RF companies with that name. A domain-only search uses the domain's label as the name. Context only, never a risk verdict. Up to seven requests. (`/v2/company` — third-party risk — needs a separate privilege and is not used.)
  - `relatedEntities` is deliberately not used: it is co-mention noise (the EICAR test hash comes out "related" to the GRU) and weighs ~90 KB. The Vulnerability module is a separate licence (`403 missing_privilege` without it), so CVEs are not queried.
- **AlienVault OTX for CVEs** (`/indicators/cve/…`, same key): OTX's own *seen in the wild* flag (→ 9) and public exploits from Exploit-DB / Metasploit… (→ 7) are the risk signals; pulses about a CVE are mostly KEV / feed roundups, so they only count for Knowledge. The ~300 KB answer is trimmed to the card's fields (20 pulses, 10 exploits). OTX takes ~60 s and then fails for a CVE it doesn't know, so the lookup gives up at 25 s (a transient timeout, left out of Knowledge).
- **AlienVault OTX** threat-actor lookups use the [pulse search API](https://otx.alienvault.com/api/v1/search/pulses) with the same `ALIENVAULT_API_KEY`. It is a full-text search over community reports, not a curated actor database ("Akira" returns phishing feeds and NFT domain lists), so the actor Summary and Activity only use pulses whose title, description or adversary names the actor or one of its aliases; the search answers return no ATT&CK ids, targets or malware, only titles and dates: results can take up to ~20 s, and MITRE ATT&CK remains the more authoritative actor profile.
- **GreyNoise** uses the free Community API: it classifies an IP as an internet-wide scanner (noise) and/or a known-good business service (RIOT). Capped at 50 lookups/week per key.
- **CrowdSec CTI** (`CROWDSEC_API_KEY`) — IP reputation built from attacks seen by the CrowdSec network: reputation (malicious / suspicious / known / safe / benign), behaviours, attack scenarios, MITRE techniques and CVEs. A known false positive (public resolver, known scanner…) or a *safe* / *benign* reputation is a clean verdict. **The free Community key has a small monthly quota** (around 120 lookups/month): consider disabling it on the home page for bulk work, and mind it when using **Test**.
- **YARAify (abuse.ch)** uses the unified `ABUSECH_AUTH_KEY`: YARA rule and ClamAV matches across every submission of a file (merged; only the latest tasks are kept). Community YARA rules are often generic (Go binary, packer…), so they only feed Knowledge; a ClamAV signature → 7.
- **CIRCL Passive DNS** (`CIRCL_PDNS_CREDENTIALS` as `user:password`, free for security teams on request) — DNS resolution history: what a domain resolved to, or which names pointed to an IP, with first / last seen. Context only (Knowledge), never a risk verdict.
- **Kaspersky OpenTIP** (`KASPERSKY_OPENTIP_API_KEY`, free with a daily quota) — Kaspersky's reputation for IPs, domains, URLs and MD5 / SHA-1 / SHA-256 hashes. The verdict is its `Zone`: Red (dangerous) → 9, Orange (not trusted) → 7, Yellow (adware / potentially unwanted) → 5, **Green (good) → clean**, Grey (not categorised) → no verdict. The rest of the answer (general info, WHOIS, categories, detections) is shown on the card as it comes, with long lists trimmed. URLs need a path, so a bare `https://host` is sent as `https://host/`. An exhausted quota answers 403, shown as `RateLimitExceeded`.
- **Google Safe Browsing** only supports URLs. It is a real-time check against Google's threat lists, so — unlike most sources — a clean result is a genuine verdict, not just "no data".

## MISP (any number of instances)

MISP and OpenCTI (next section) are the sources you can add several times: your own instance, a partner's, an ISAC feed… Each one shows up as its own named source with its own status and toggle. Admins add, edit and delete them on the **Connectors** page (name, URL, API key, TLS verification, mTLS certificate) and the change applies to the next lookup, no restart. The UI renders each with a shared card.

Instances defined in `backend/.env` (the `MISP_<N>_*` block in `backend/.env.example`) keep working: they are used until the first MISP change on Connectors, which copies them into `backend/data/connectors.json` — from then on `MISP_<N>_*` is ignored. Instance ids (`misp_<N>`) are never reused after a delete, so a new instance doesn't inherit an old one's weights.

- **Search** — by indicator value only (not MISP's `ip-src` / `ip-dst` / … attribute types), so it works the same for IP, domain, URL and hash regardless of how a community tags its attributes.
- **Scoring** — only attributes flagged for detection (`to_ids`, shown as an **IDS** chip) count as a risk hit (subscore 9). A match whose attributes all have `to_ids` off — typically benign infrastructure referenced inside an event, like a public DNS resolver — adds to Knowledge but issues no risk verdict (and is never treated as clean).
- **Weights** — set on the Admin page. New instances start at 0 / 9; instances imported from `.env` start at `MISP_<N>_WEIGHT` / `MISP_<N>_KNOWLEDGE_WEIGHT`. A value saved in Admin wins.
- **Mutual TLS** — some instances (common on government / CERT deployments) reject requests without a client certificate. Drop the cert (and key, if separate) into `backend/certs/` (gitignored, mounted read-only at `/app/certs`) and pick them in the instance's **Client certificate** / **Client key** on Connectors (or `MISP_<N>_CLIENT_CERT` / `_CLIENT_KEY` in `.env`). A combined cert+key PEM only needs the certificate.

## OpenCTI (any number of instances)

Works exactly like MISP: each instance (yours, a partner's, a sector ISAC's…) is its own named source, added / edited / deleted on **Connectors** with the same fields — name, URL, **API token**, TLS verification, mTLS certificate — or as `OPENCTI_<N>_*` in `backend/.env` until the first OpenCTI change there. Ids are `opencti_<N>`, never reused. Use the token of a **dedicated read-only user** (OpenCTI → Profile → API access): the instance sees its markings, so it only returns what that user may read. Requires **OpenCTI 6.0 or newer** (GraphQL API at `<url>/graphql`).

- **Types** — IP, domain, URL, hash, threat actor and CVE (MISP: the first four).
  - *IP / domain / URL / hash*: the observable with that exact value (or any of its MD5 / SHA-1 / SHA-256 / SHA-512 hashes) and its indicators, plus indicators whose STIX pattern names the value but have no observable (feeds imported without “create observables”).
  - *CVE*: the Vulnerability entity — CVSS, and on recent releases EPSS, CISA KEV, CWE and SSVC.
  - *Threat actor*: intrusion sets and threat actors (groups / individuals) matched on name or alias; the closest result is shown with a warning when nothing matches exactly. Its context query asks for up to 300 relationships and 25 reports, with each related entity's ATT&CK id, observable value and indicator pattern: they feed the actor Summary (TTPs, CVEs, targets, related artifacts, campaigns / incidents, arsenal).
  - For every match, its **reports** and **relationships** (malware, actors, campaigns, vulnerabilities…) — they feed the card and the Summary's families, actors and campaigns.
- **Scoring** — only **active indicators** (not revoked, `valid_until` still in the future when the lookup ran — frozen in the history) are a risk verdict: their OpenCTI score ÷ 10 (7 when unscored). An observable without an active indicator is context: OpenCTI gives every observable a default score of 50, which says nothing. CVE: in CISA KEV → 9; related to an actor / malware / campaign → 8. Threat actors: context only. Never a clean verdict.
- **Versions** — queries with fields from recent releases (CVSS v4, EPSS, KEV, SSVC) fall back automatically to a compatible version on older platforms. `backend/tests/opencti_schema_check.py` validates every query against the GraphQL schema of any release, without an instance.
- **Weights** — like MISP: new instances start at 0 / 9 (`OPENCTI_<N>_WEIGHT` / `_KNOWLEDGE_WEIGHT` for `.env` ones); set them on Admin.
